# Сайт-аналитика iiko — что умеет

Веб-кабинет владельца ресторанной сети поверх iiko. Ветка `feat/paper-design`,
код фронта — `web/src/lg/`, бэк — `api.py` (FastAPI). Данные живые: iikoWeb OLAP
(аналитика), iiko Cloud (живой зал), собственный КДС saya-kds (кухня и доставка).

Обновлено: 2026-08-11.

---

## Как устроено в целом

**Мультифилиальность.** Владелец видит только свои рестораны (`/api/restaurants`
по telegram-id). Переключатель филиала в шапке; выбор сохраняется между
перезагрузками (`localStorage`, ключ `lg:org`) и проверяется по списку — чужой
или удалённый филиал не переживёт смену аккаунта. Все экраны перезапрашиваются
при смене филиала. Принцип «изоляции»: каждый филиал видит свои данные, это не
сравнение филиалов между собой.

**Период.** Общий фильтр в шапке (Сегодня / Вчера / Неделя / Месяц) для экранов,
помеченных как периодические. Тоже переживает перезагрузку.

**Навигация.** Нижний плавающий док на десктопе (все 16 разделов), на узких
экранах — таб-бар из трёх основных + кнопка «Ещё» с полным списком по группам.

**Тема.** Светлая по умолчанию, есть ночная; выбор сохраняется.

**Демо-режим.** Организация `demo-org-1` отдаёт демо-данные без авторизации.
Сборка с `VITE_BAKED=1` работает офлайн на вшитых ответах; в обычной сборке этих
данных нет вовсе.

## Разделы

### Сводка

**Ресторан** (`home`) — оперативный экран смены.
- Заказы по типам за сегодня: зал / доставка / агрегаторы — количество и выручка.
- Живой план зала из iiko Cloud (`/api/hall`): столы с реальной расстановкой,
  занятые / бронь / свободные, гости и сумма по столу. Переключатель залов, если
  секций несколько. Столы, не расставленные на схеме в iiko, показываются
  отдельным списком; если схемы нет вовсе — фальшивый пол не рисуется.
- Плитки: гости сейчас, открытые заказы, загрузка зала, выручка сегодня, оборот
  стола, бронь на вечер (последнее — только если у филиала включён модуль броней).
- Лента активности по занятым столам.

**Директор** (`director`) — оценка «здоровья» ресторана.
- Сводный балл по нескольким параметрам с весами.
- «Куда уходит выручка» — разложение по статьям.
- «Как снизить · план» — сколько можно вернуть в месяц по каждому пункту.
- «План месяца · в работе» — задачи с шагами: что сделать, сколько это стоит,
  насколько долго.
- Источники: фудкост, отмены, списания, склад, расходы, отзывы, ИИ-инсайты.

**Главная** (`dash`) — деньги за период.
- Выручка за период с динамикой, график по дням (пик подсвечен).
- Прогноз месяца при текущем темпе.
- Средний чек, гости, открытые заказы.

### Деньги

**Фудкост** (`fc`) — себестоимость по техкартам.
- Факт против нормы, перерасход в тенге за период.
- Тренд по месяцам, разбор блюд по проценту себестоимости.
- Если техкарты или приходные цены не заполнены — экран честно говорит, что
  считать не из чего, и ставит это планом, а не показывает ноль.

**Меню · продажи** (`menu`).
- Меню-инжиниринг: что тянет выручку, что балласт.
- Категории меню, каналы продаж, способы оплаты.
- «С чем берут» — сопутствующие позиции в чеке (корзина).

**Расходы** (`exp`) — расходы за период, включая ручные.

**Склад · заявки** (`supply`).
- Строгий баланс по позиции: было + приход − остаток = ушло, сверка с продажами,
  расхождение в тенге (недостача / фрод / списание).
- Стоп-лист: ходовые позиции с нулём в остатке = упущенная выручка.
- Списания по категориям, отмены заказов, изъятия из кассы.
- Закуп по поставщикам и что пришло по накладным.

**Год к году** (`yoy`) — текущий год против прошлого: выручка и заказы помесячно,
сколько месяцев в плюсе, разрыв по каждому месяцу.

### Операции

**Смены и персонал** (`staff`).
- Официанты: выручка, заказы, время начала смены.
- Курьеры: доставки, среднее время в пути, процент опозданий.
- Час-пик по дням недели: пиковый час каждого дня — когда ставить больше людей.
- **Опоздания по доставкам** — из OLAP «Заказы-доставка»: сколько доставок
  опоздало по этому филиалу и каждое опоздание поимённо (номер заказа, дата,
  курьер, адрес, обещанное и фактическое время, опоздание, сумма). Самовывоз
  отсекается — это не доставка. Опоздания больше двух часов помечаются: обычно
  это не курьер, а заказ, который забыли закрыть в iiko.
- **Кухня по зонам · час** и **карта доставки** — из собственного КДС saya-kds
  (см. ниже).

**Расписание** (`sched`) — план смен на неделю (хранится на устройстве) против
факта явок из iiko (`/api/attendance`), со статусами по каждому сотруднику.

**План** (`plan`) — недельный план по количеству заказов на три типа: зал,
доставка, агрегаторы. План хранится в БД (доступен со всех устройств владельца),
факт подтягивается из продаж. Вписал план на неделю — предлагает проставить на
весь месяц.

### Гости

**Клиенты · RFM** (`clients`) — сегментация клиентской базы, топ-VIP, удержание,
идеи по работе с сегментами.

**Соцсети** (`rep`) — рейтинги площадок (2ГИС, Wolt), лента отзывов, тональность
и темы жалоб.

### Витрина

**Отчёт недели** (`mocks`) — сводка для владельца: что улучшилось за неделю, как
идём по плану, приоритеты следующей недели.

**Виджеты iOS** (`widgets`) — личная ссылка на веб-виджет для домашнего экрана
(выручка за сегодня + кнопка отправки накладной в бот).

### Настройки

**Подключить** (`connect`) — онбординг: подключение iiko-сервера (аналитика) и
Cloud apiLogin (живой зал), привязка площадок отзывов. Пароли шифруются.

## ИИ-директор (ассистент)

Проактивный советник, а не чат. Кнопка справа внизу на всех экранах.

- Сам смотрит **все филиалы** владельца и выдаёт разбор «проблема → деньги → что
  сделать», сгруппированный по филиалу, с кнопкой перехода в нужный раздел.
- **Хвалит за результат** (зелёные карточки, счётчик «✓ N» отдельно от проблем):
  за выполненный недельный план и за выросший показатель — выручка, средний чек,
  снизившийся фудкост, поднявшийся рейтинг. Сравнение недели идёт к прошлой
  неделе, обе — полные.
- Причину роста называет **только когда она видна в данных** и влияет именно на
  этот показатель: выручка ← разобранный стоп-лист или упавшие отмены, фудкост ←
  заполненные техкарты или убранные списания. Средний чек и рейтинг — без
  причины. Выдуманное «благодаря вашей работе» обесценивает похвалу.
- Чтобы знать «было», раз в 20 часов пишется снимок показателей филиала
  (таблица `signal_snapshots`).
- Если план занижен (факт кратно выше) — хвалит, но говорит, что планку пора
  поднять.

**Деньги.** Платная модель включается только явным `ASSISTANT_AI=1`; без него
работают бесплатные детерминированные правила. Ответ кэшируется на 12 часов
(`ASSISTANT_TTL_HOURS`), потолок токенов — `ASSISTANT_MAX_TOKENS`. Переменная
`ASSISTANT_SNAPSHOT` отдаёт сохранённый разбор из файла — для показа без трат.

## Данные из собственного КДС (saya-kds)

Через прокси `/api/chaspik` (ключ живёт на бэке, во фронт не попадает). Считает
один филиал — `CHASPIK_ORG_ID`, поэтому эти карточки не следуют переключателю
филиалов.

- **Кухня по зонам · час** — таблица-хитмап зона × час (пицца, роллы, горячий
  цех), пиковый час, среднее время готовки по зоне.
- **Путь заказа** — сколько минут занимает каждый этап до клиента: готовка,
  сборка, ожидание курьера, доставка, и общий итог.
- **Карта доставки** — инлайновый SVG без тайлов и библиотек: точка = адрес,
  размер и число = сколько раз оттуда заказывали. Медиана доставки в подзаголовке.

## Технические ограничения, которые стоит помнить

- **Фильтр филиала в OLAP работает по названию, а не по UUID** — самохостед
  iikoWeb на UUID отдаёт ноль строк.
- **Схема зала**: iiko отдаёт размер холста, который бывает меньше реальной
  расстановки — габариты считаются по фактическим столам, иначе они уезжают за пол.
- **Псевдо-секции** (вынос, доставка, Wolt/Glovo, в том числе кириллицей
  «Вольт»/«Глово») не показываются как залы — они уходят в каналы.
- **Дельты в `/api/dashboard`** (`revenue_change` и прочие) возвращаются нулями —
  недельные изменения считаются отдельно.
- Первый запрос ассистента идёт ~30 секунд: 13 филиалов × 9 обращений к iiko.
