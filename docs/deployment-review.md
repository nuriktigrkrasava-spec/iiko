# Проверка перед развёртыванием исправлений ревью

Этот документ не означает, что production уже проверен или обновлён. Не применяйте
Blueprint к существующему сервису без сверки диска, переменных и резервной копии.

## До остановки работающего сервера

1. Убедитесь, что заданы `TELEGRAM_BOT_TOKEN`, `ENCRYPTION_KEY` и
   `TELEGRAM_WEBHOOK_SECRET`. Без любого из них production не стартует.
   Тот же webhook secret должен быть зарегистрирован в Telegram `setWebhook`.
   Не меняйте `ENCRYPTION_KEY`: существующие пароли в БД зашифрованы этим ключом.
2. Сохраните SQLite через online backup API, проверьте integrity_check и
   восстановление на отдельном сервере. Учитывайте также загруженные файлы.
3. На существующем сервисе база находится в `/data/iiko_boss.db`.
   `render.yaml` использует этот же путь. Имя диска `iiko-data` и размер 1 GB
   в Blueprint — параметры НОВОГО сервиса, а не подтверждённые настройки старого.
   Для переноса проверьте mount `/data`, фактическое имя, размер и свободное место
   в панели хостинга. Не создавайте пустой диск вместо существующего.
4. Запустите `python scripts/check_deployment.py --check-tls` с окружением
   целевого сервера ДО перезапуска. Скрипт читает БД в режиме read-only, не создаёт
   новую и не выводит значения секретов или URL с паролями. TLS-проверка обращается
   только к хостам из разрешённого списка, без передачи логина/пароля.

## Прокси и ограничения частоты запросов

`TRUSTED_PROXY_CIDRS` — через запятую адреса/сети доверенных reverse proxy.
Без него заголовок `X-Forwarded-For` игнорируется: это безопасно против подделки,
но все посетители за одним прокси получают общий лимит. На Render preflight
считает отсутствие этого значения ошибкой, для прямого соединения — предупреждением.

Уточните реальный TCP peer и цепочку прокси в конфигурации инфраструктуры.
Если измеряете peer, логируйте только `request.client.host`, кратковременно,
без URL, токенов, заголовков и тела запроса. Проверьте, не переписывает ли Uvicorn
адрес клиента раньше приложения: доверие должно настраиваться на одном уровне.
Не берите сеть из присланного пользователем X-Forwarded-For; не доверяйте `*`,
`0.0.0.0/0` или `::/0`. Не угадывайте адреса Render и не переносите их на свой nginx.

После настройки проверьте: два внешних IP имеют разные лимиты, а поддельный
левый элемент X-Forwarded-For не меняет лимит. Код проходит цепочку справа налево
до первого недоверенного адреса, поэтому несколько ваших прокси не сливаются в один.

## iiko, таблицы и 2ГИС

В production разрешены только HTTPS, порт 443, действующий TLS-сертификат.
Хосты `*.iiko.it` разрешены; дополнительные точные имена задаются оператором в
`IIKO_TRUSTED_HOSTS`. Не добавляйте домен автоматически на основании ввода клиента.
Проверьте ВСЕ уникальные сохранённые серверы. Самоподписанные сертификаты нужно
заменить или настроить доверенную инфраструктуру отдельно; `verify=False` запрещён.
Для CSV дополнительные разрешённые хосты задаются в `CSV_TRUSTED_HOSTS`.

`REVIEWS_2GIS_KEY` и `CATALOG_2GIS_KEY` — разрешённые вашему сервису ключи 2ГИС.
Их отсутствие отмечается preflight; проверьте реальные отзывы после настройки.
Ключей в репозитории быть не должно. Наличие ключа не доказывает действующий тариф
или доступ к API, поэтому нужна отдельная функциональная проверка вкладки.

## Сравнения и недоступные филиалы

История «Что изменилось» берётся из БД отдельно для каждого владельца и филиала.
`ASSISTANT_SNAPSHOT_OWNER_ID` ограничивает только внешний JSON-файл
`ASSISTANT_SNAPSHOT`, но не сравнения в БД. Общий файл нельзя отдавать другим клиентам.

Если не удалось прочитать один филиал, сводка сети остаётся недоступной:
неполные числа нельзя показывать как итог всей сети. Остальные филиалы можно
открыть отдельно. Частичные итоги потребуют отдельного интерфейса с явным перечнем
недоступных филиалов; маскировать ошибку нулевой выручкой нельзя.

## Старые ссылки виджетов: точечный отзыв

Старый `/w/{owner_token}/{org}` содержит право на всю сеть, независимо от org
в адресе. Его нельзя превращать в безопасную ссылку простой заменой пути.
Новые ссылки управляющим выдавайте через branch widget token.

Для отзыва уже выданных виджетов выбранного владельца добавьте/увеличьте его
версию в `WIDGET_OWNER_VERSIONS` (JSON, например `{"123":1}` для вымышленного uid).
Сначала согласуйте время, затем перезапустите сервис с этой настройкой и
перевыпустите ссылки виджетов и `/j` журналов этого владельца. Старые owner- и
branch-widget токены перестанут работать даже при наличии ответа в кэше.
Другие владельцы, личные `/m` ссылки, вход в мобильку и приглашения не меняются.

Нельзя удалять или уменьшать версию: это восстановит старые ссылки.
Сохраните эту карту при переносе сервера. Без изменения версии старые ссылки
сохраняются для совместимости: добавление кода не является их фактическим отзывом.
Общий `WIDGET_SECRET` для этого менять не нужно; не меняйте ключ шифрования БД.

## Мобильный вход и push

`NATIVE_STAFF_ENABLED`, `NATIVE_JOIN_ENABLED`, `NATIVE_APP_ORIGIN`,
`PUSH_ENABLED`, `FIREBASE_PROJECT_ID`, `FIREBASE_SERVICE_ACCOUNT_FILE`
описаны в `.env.example`. По умолчанию новые функции выключены. Сервисный ключ
Firebase хранится отдельно от Git; включение требует проверки реального сценария.
