# Дизайн: выбор филиала в «Плане» + выбор дня и синхрон даты (Главная/Продажи)

Дата: 2026-06-11
Статус: согласован, готов к плану реализации

## Контекст

Telegram Mini App аналитики ресторанов. Фронт — один файл `index.html` (Vanilla JS),
бэк — `api.py` (FastAPI), `iiko.py` (клиент iiko). Единый глобальный `state` на фронте.

Две независимые задачи, заказанные шефом (telegram id `355897224`):

1. В суб-вкладке **«План»** (внутри таба «Год/год» / comparison) нет выбора филиала —
   план жёстко считается по первому филиалу. Шеф с несколькими филиалами не видит остальные.
2. На вкладках **«Главная»** и **«Продажи»** дата выбирается раздельно (нет синхрона),
   и нельзя выбрать один конкретный день — только пресеты и произвольный диапазон.

## Что НЕ трогаем

- Бэкенд `/api/plan/{org_id}` — уже принимает один `org_id`, логика год/недели остаётся.
  «План» расписан на год по неделям; переключателя времени там нет и не нужно.
- Логику парсинга плана из Google-таблицы и OLAP-факта.
- Таб «Год/год» в остальном (только добавляем чип филиала в суб-вкладку «План»).

## Часть A — Выбор филиала в суб-вкладке «План» (только шеф)

### Поведение

- Компактный чип-плашка в `#comp-view-plan`, над `#plan-table-wrap`:
  `🏢 <Название филиала> ▾`.
- Тап по чипу → лёгкий sheet (single-select) со списком всех филиалов
  (`state.restaurants`), по стилю существующих модалок (`.modal-overlay` / `.modal-sheet`).
- Выбор филиала → план перезагружается под этот org.

### Состояние

- Новое поле `state.planOrgId` (по умолчанию `null`).
- `loadPlan()`: `const orgId = state.planOrgId || getActiveOrgIds()[0] || state.restaurant.organization_id;`
- В рамках сессии, **без** localStorage. При смене активного филиала/мультивыбора —
  сбрасывать `state.planOrgId = null` (чтобы не показывать план филиала, который больше не выбран).

### Гейтинг (только шеф)

- Telegram id берём на фронте: `window.Telegram?.WebApp?.initDataUnsafe?.user?.id`.
- Константа вверху скрипта: `const PLAN_BRANCH_SWITCHER_TG_ID = 355897224;`
- Чип филиала рендерим в «Плане» только если
  `myTgId === PLAN_BRANCH_SWITCHER_TG_ID` **и** `state.restaurants.length > 1`.
- Это чисто UI-гейт: бэк и так отдаёт план только по своим филиалам пользователя,
  поэтому клиентской проверки для показа плашки достаточно.

### Бэкенд

- Без изменений. Просто шлём выбранный `orgId` в существующий `/api/plan/{org_id}`.

## Часть B — Выбор дня/периода + синхрон (Главная / Продажи)

### Синхрон даты — единый источник правды через центральный сеттер (выбранный подход)

Цель: дата/период едины для Главной и Продаж — изменил на одной, отразилось на другой.

Реализация (с минимальным радиусом правок): поля `state.salesPeriod`/`state.salesCustomRange`
читаются в ~10 местах (cancels, companions, fetchOlap, кэш). Чтобы не выпиливать их из всех
мест (риск пропустить), держим **обе пары полей в жёсткой синхронизации через один сеттер**:

- Новая функция `applyGlobalPeriod(period, customRange)` — единственная точка записи периода.
  Пишет одновременно: `state.period = state.salesPeriod = period` и
  `state.customRange = state.salesCustomRange = customRange`. После этого они всегда равны →
  любой существующий read-site остаётся корректным без правок.
- `applyGlobalPeriod` также перерисовывает подсветку чипов **обеих** панелей
  (`#main-date-filters` и `#sales-date-filters`) и текст обоих чипов «Даты» из стейта
  (отдельная функция `renderDateFilters()`), затем перезагружает данные обеих вкладок
  (`loadDashboard()` всегда; `loadSales()` + sales-подвкладки).
- `setPeriod(p, el)` и `setSalesPeriod(p, el)` делегируют в `applyGlobalPeriod(p, null)`.
- `applyDateRange()` делегирует в `applyGlobalPeriod('custom', range)`.
- Обе панели фильтров всегда в DOM (видимость переключается экранами), поэтому
  обновление подсветки сразу для обеих панелей делает переключение вкладок корректным
  без отдельного ресинка в `switchTab`.
- `cacheKeyFor`/`buildPeriodQuery` не меняем.

Отклонённый вариант: физически удалить `salesPeriod`/`salesCustomRange` и переписать все
read-sites — функционально то же, но больший радиус и риск пропустить место.

### Модалка дат — тумблер «День / Период»

`#date-range-modal` получает переключатель режима наверху:

- **День**: один `input type=date` (`#dr-day`). Выбор дня → `customRange = {from: d, to: d}`,
  `period = 'custom'`. Чип: `📅 05.06`.
- **Период**: два поля С/По (`#dr-from` / `#dr-to`), как сейчас. Чип: `📅 05.06–20.06`.
- Применение (`applyDateRange`) учитывает активный режим. Валидация: для периода `from <= to`.
- При открытии модалки режим определяется по текущему `customRange`
  (если `from === to` → режим «День», иначе «Период»; по умолчанию «День», дата = сегодня).

### UI-замечания

- Чип «📅 Даты» остаётся один и тот же в обеих панелях; меняется только его текст.
- Пресеты (Сегодня/Вчера/Эта неделя/Этот месяц) работают как раньше, но теперь
  синхронны между вкладками.
