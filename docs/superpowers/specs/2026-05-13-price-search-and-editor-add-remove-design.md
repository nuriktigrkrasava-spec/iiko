## 1. Цель

Две связанные фичи, оба чисто аддитивные (без модификации существующих эндпоинтов, схем, поведения):

1. **Поиск цен по номенклатуре (`📊 Цены`)** — подвкладка в «Накладные», даёт ввести любой товар iiko и видеть таблицу его цен по всем поставщикам за период (источник: iiko + локальные `bot_invoices`).
2. **Редактор накладной — add/remove позиций** — в существующем `screen-invoice-edit` появляются 🗑 на каждой строке и ➕ «Добавить позицию» внизу.

### 3.3 Backend: `GET /api/price-stats/{org_id}`

**Query params:**
- `product_id` (required) — iiko product GUID из номенклатуры
- `days` (default 180, max 365) — окно истории

**Возвращает:**
```json
{
  "product": {"id": "...", "name": "Помидоры красные", "unit": "кг"},
  "best": {
    "supplier_name": "Sapa Foods",
    "supplier_id": "...",
    "price_per_unit": 480.0,
    "date": "2026-04-28",
    "unit": "кг"
  } | null,
  "suppliers": [
    {"supplier_name": "...", "supplier_id": "...",
     "price_per_unit": 480.0, "date": "2026-04-28",
     "unit": "кг", "delta_pct": 0.0}
  ],
  "stats": {"purchases": 8, "days": 180}
}
```

**Реализация:**

1. Получить из iiko список приходных накладных за `days` дней — переиспользуем существующий `IikoClient.get_invoices` / `get_documents_export_invoice_incoming` (см. `iiko.py` где это уже используется для вкладки Накладные).
2. Распарсить каждую накладную, найти позиции с `productId == product_id`.
3. Для каждой совпавшей позиции — `price_per_unit = sum/amount` (или взять `price` если он есть в выгрузке).
4. **Фильтр по единицам**: оставить только позиции с тем же `unit` что у запрошенного товара (если iiko в выгрузке отдаёт unit на позицию). Если unit разный — пропустить с записью в `notes` (или просто не показывать).
5. Догрузить локальные `bot_invoices` за тот же период (через расширение `get_price_history` или новую функцию) — там у позиций может быть `iiko_product_id` который сматчит точно с `product_id`.
6. Группировать по `supplier_id || supplier_name`, для каждого поставщика — взять МИНИМАЛЬНУЮ цену.
7. Отсортировать по цене возрастанию.
8. `best` = первый элемент (или null).
9. `delta_pct` для каждого относительно `best`.

**Кеш:**
- Список накладных iiko за org+date_range кешим в `IikoClient` на 1 час (паттерн уже есть для номенклатуры в `search_nomenclature`).
- Кеш по ключу `org_id|days` — не по `product_id`, чтобы повторные поиски в той же сессии не дёргали iiko.

## 4. Фича B: Редактор накладной — add/remove позиций

### 4.1 UI

В `screen-invoice-edit`, секция `ie-items`:

Каждая строка-позиция уже имеет:
- name, qty, unit, price, total
- ✏️ кнопка редактирования

**Добавляем:**
- 🗑 кнопка справа от ✏️ → `onclick="ieDeleteItem(idx)"` → `confirm('Удалить позицию?')` → splice из `ieState.items` → `ieRenderItems()` + `ieRecalcTotals()`

**В конце списка `ie-items`** (после последней `.ie-item`):
- Кнопка `<button class="ie-add-btn" onclick="ieAddItem()">➕ Добавить позицию</button>`

`ieAddItem()`:
- Создаёт новый item с `{name:'', quantity:0, unit:'кг', price_per_unit:0, total:0}`
- Пушит в `ieState.items`
- Открывает существующую модалку редактирования через `ieOpenEditModal(ieState.items.length - 1)` чтобы пользователь сразу заполнил поля + выбрал товар iiko через поиск номенклатуры
- Если пользователь жмёт «Отмена» в модалке без сохранения — удалить эту пустую позицию обратно
  - **Реализация:** ввести `ieState._addingNew = idx` при добавлении, в `ieCloseModal` если `_addingNew !== null` и пользователь не сохранил — `splice(_addingNew, 1)` и `ieRenderItems()`. Если сохранил (через `ieSaveItem`) — сбросить `_addingNew = null`.

### 4.2 Backend

Ничего не меняем. `/api/invoice-edit/{pid}` (`api.py:1485`) и `/api/invoice-saved/{id}/send` (`api.py:1587`) уже принимают `items: List[Dict]` без проверки минимального/максимального количества.

## 5. Edge cases

| Случай | Поведение |
|---|---|
| `📊 Цены`: товар выбран, но за 180 дней нет накладных в iiko и нет в bot_invoices | Карточка с «📭 За 180 дней закупок этого товара не было» |
| `📊 Цены`: iiko-запрос упал | Тост `❌ Не удалось загрузить историю iiko: <err>`, карточка не рисуется. Кешированные локальные данные показываем если есть, с пометкой `⚠️ показаны только данные бота, iiko недоступен` |
| `📊 Цены`: позиции в iiko у одного товара в разных единицах (кг и шт) | Группируем по unit. Если в `best` оказался unit отличный от запрошенного — добавляем в карточку флаг `⚠️ единицы не совпадают` |
| `📊 Цены`: один поставщик закупал товар несколько раз с разными ценами | Берём МИНИМАЛЬНУЮ цену этого поставщика. В UI рядом с датой можно дописать «(мин из N закупок)» — опционально |
| Редактор: удаляем последнюю позицию | Список пустеет, total = 0. Кнопка «💾 Сохранить» остаётся доступной (можно сохранить пустую накладную; пусть пользователь сам отменит если не хочет) |
| Редактор: добавил позицию, ввёл данные, нажал «Сохранить» в модалке — закрылась модалка, `_addingNew` сброшен | Позиция в списке остаётся, рендер обновлён |
| Редактор: добавил позицию, нажал «Отмена» в модалке | Пустая позиция удаляется из `ieState.items`, `_addingNew` сбрасывается, рендер обновлён |
| Редактор: добавил позицию, не выбрал товар iiko, сохранил | Позиция остаётся с пустым `iiko_product_id`. При попытке «Отправить в iiko» — улетит в `needs_mapping` (текущее поведение) |

## 8. Out of scope

- **Аналитика по нескольким товарам сразу** (рейтинг «самые дорогие закупки за месяц» по всему ассортименту) — может быть отдельной итерацией.
- **Фильтр по конкретному филиалу при сравнении** — пока берём `state.restaurant.organization_id` (текущий выбранный). Multi-branch агрегация цен — позже.
- **Графики динамики цен** — текстовая таблица, без spark-lines.
- **Экспорт сравнения в CSV** — нет, в Mini App данные одноразовые, не для отчёта.
- **Drag-and-drop reorder позиций** в редакторе — не делаем.
- **Сравнение в боте (`📊 Сравнить цены`)** — остаётся неизменным, не переключаем источник на iiko (это другой контекст и трогать без необходимости — нарушение «не меняй что есть»). Если впоследствии захочешь объединить — отдельная итерация.
