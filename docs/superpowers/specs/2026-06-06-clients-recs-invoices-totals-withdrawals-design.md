# Рекомендации по клиентам, итоги накладных, изъятия — дизайн

Дата: 2026-06-06
Статус: согласовано (фичи 1–3), баг ссылок — расследование в ходе реализации

## Контекст

iikoBoss — Telegram Mini App аналитики ресторанов (FastAPI + SQLite + Vanilla JS).
Стек и архитектура: см. память проекта. Работа затрагивает `api.py`, `iiko.py`,
`index.html`, `database.py`.

Набор задач этой итерации:

1. Клиенты: рекомендации по конкретному клиенту при клике.
2. Накладные: переключатель периода (день/неделя/месяц) + строка «Итого».
3. Изъятия: новая суб-вкладка в разделе Расходы (данные из iiko OLAP).
4. Баг: ссылка во вкладках «План» / «Клиенты» не сохраняется — найти и устранить.
5. (Сделано) Личные данные в инструкции бота — реальный хостнам заменён на плейсхолдер.

## 1. Клиенты: карточка клиента + рекомендация

### Текущее состояние
- `_clients_segments` (`api.py:1733`) уже считает `loyal_revenue` (сколько принесли
  лояльные, заказов ≥ 2) и `loyal_potential` (сколько ещё могут принести, если довести
  лояльных до 10 заказов по текущему среднему чеку). Эти поля **не выводятся** в UI.
- `renderClients` (`index.html:2297`) рисует сегменты + таблицу «Топ клиенты»
  (телефон/заказов/сумма) из `top_vip`. Строки некликабельны.

### Изменения
**Backend:** изменений в расчёте не требуется — `loyal_revenue` и `loyal_potential`
уже в ответе. Доп. запросов в iiko нет.

**Frontend (`renderClients`):**
- После сетки сегментов — плашка: «Лояльные принесли `loyal_revenue` · могут принести
  ещё +`loyal_potential`».
- Строки таблицы «Топ клиенты» делаются кликабельными. По клику под строкой
  раскрывается мини-карточка (toggle):
  - Принёс: `spend` · Заказов: `orders` · Средний чек: `round(spend/orders)`
  - Рекомендация (текст по правилу):
    - `orders < 10`: «До VIP осталось `10−orders` заказов ≈ **+`(10−orders)·средний чек`** ₸»
    - `orders >= 10`: «VIP-клиент. Удержание: персональная акция / привилегия»
- Средний чек и потенциал считаются на фронте из уже имеющихся `top_vip` полей.

### Граничные случаи
- `orders == 0` в `top_vip` отфильтрованы ещё в бэке (там `orders >= 1`).
- Телефон уже маскируется (`_mask_phone`), карточка не раскрывает полный номер.

## 2. Накладные: переключатель периода + Итого

### Текущее состояние
- Фронт зовёт `/api/invoices/{org}?period=week` жёстко (`index.html:2769`).
- `invoices` (`api.py:1074`) принимает `period`, использует `get_period_dates`
  (умеет `today/week/month/custom`). Бот-накладные подмешиваются, но режутся
  `get_bot_invoices(limit=10)` — для суммы за месяц этого мало.
- Общей суммы в ответе и в UI нет.

### Изменения
**Backend (`invoices`):**
- В ответ добавить `total_amount` (сумма `amount` по всем накладным периода) и
  `count`. Считать ДО обрезки списка для отображения.
- Бот-накладные: для подсчёта `total_amount` брать все накладные периода
  (по дате в диапазоне `date_from..date_to`), а не последние 10. Список для
  отображения может оставаться обрезанным, но сумма должна быть полной.
  Реализация: расширить/убрать `limit` при выборке для агрегата, фильтровать по дате.

**Frontend (вкладка Накладные):**
- Над списком — пилюли «День / Неделя / Месяц» (стиль `.subtab`), дефолт — Месяц.
- Состояние периода в `state.invoicePeriod` (дефолт `month`).
- Строка «Итого за период: `count` накладных на сумму `total_amount`».
- Переключение пилюли → перезапрос `/api/invoices/{org}?period=...` → перерисовка.

### Граничные случаи
- Пустой период: «Итого: 0 накладных», список пуст.
- Кэш `_cache_key` уже включает `period` — разные периоды кэшируются отдельно.

## 3. Изъятия: новая суб-вкладка

### Подход
Изъятия наличных (выемка/инкассация из кассы) — движение денег, не операционный
расход. Держим отдельно, чтобы не раздувать «Расходы». Реализация — тем же
механизмом OLAP `TRANSACTIONS`, что списания/расходы (`iiko.py:646-730`).

### Изменения
**iiko.py — новый метод `get_cash_withdrawals(org_ids, date_from, date_to)`:**
- OLAP `reportType: "TRANSACTIONS"`, фильтр по типу кассовой операции изъятия.
- **Точный код типа транзакции подтвердить через columns-introspection iiko ДО
  реализации** (URL интроспекции — в памяти `reference_iiko_olap_fields`). Не зашивать
  код наугад. Кандидаты: тип операции «Изъятие наличных» / выемка из кассовой смены.
- Возвращает `{"withdrawals": [{"date", "sum", "comment"/"account"}]}`.

**api.py — новый эндпоинт `/api/withdrawals/{org_id}?period=...`:**
- По образцу `writeoffs`/`expenses`: демо-ветка, кэш, `_olap_dept`, fallback на демо.
- Ответ: `{"withdrawals": [...], "total": <сумма>}`.

**index.html:**
- Новая суб-вкладка «Изъятия» в `#expense-tabs`, ветка в `setExpenseTab` и
  `loadExpenses`.
- UI: «Итого изъято за период: X» + список (дата · сумма · комментарий/счёт) +
  тот же переключатель периода, что у накладных.

### Граничные случаи
- Изъятия не ведутся через кассовые смены → пустой список «Нет изъятий за период».
- Демо-режим — статичные демо-данные (как `DEMO_WRITEOFFS`).

## 4. Баг: ссылка не сохраняется (План / Клиенты)

### Что проверено
- Запись/чтение корректны: UPSERT в `plan_links`/`client_links`
  (`database.py:447-481`), таблицы создаются в `init_db`. Save и load используют
  один `org_id` (`_get_org_id` возвращает тот же id).

### Гипотезы (расследовать по systematic-debugging)
1. **БД на эфемерном диске Render (наиболее вероятно).** `DB_PATH` по умолчанию
   `iiko_boss.db` в рабочей директории (`database.py:8`). Если на Render `DB_PATH`
   не указывает на persistent disk — файл стирается при редеплое вместе со ссылками,
   бот-накладными и ручными расходами.
2. **Код-баг** в режиме «Все филиалы» / demo (`getActiveOrgIds()[0]` vs контекст).

### План фикса
- Сначала воспроизвести/локализовать: проверить `DB_PATH` на проде и наличие
  persistent disk; проверить, что save и последующий load дают один `org_id`.
- Если причина — диск: задать `DB_PATH` на смонтированный persistent disk и/или
  сделать дефолт устойчивым (использовать каталог persistent disk, если он есть).
- Если код-баг: исправить рассинхрон ключа.
- Не делать необратимых изменений со схемой/данными без подтверждения.

## Вне scope (информационно)
Вопрос «какие ещё данные можно достать через OLAP» — отвечено в обсуждении
(себестоимость/маржа, скидки, типы оплат, удаления блюд, загрузка по часам,
оборот по поставщику). В build этой итерации **не входит** — отдельные фичи при
запросе.

## Порядок реализации
1. Клиенты (только фронт, без iiko-запросов) — самый быстрый и безопасный.
2. Накладные (бэк `total` + фронт переключатель).
3. Баг ссылок (расследование + фикс).
4. Изъятия (требует подтверждения OLAP-кода через introspection).
