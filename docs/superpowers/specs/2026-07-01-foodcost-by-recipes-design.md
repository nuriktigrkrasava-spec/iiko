# Дизайн: Фудкост по техкартам (для самохостед iikoWeb)

**Дата:** 2026-07-01
**Ветка:** feat/demo-trial (продолжение)
**Статус:** утверждён владельцем (делегировал реализацию), готов к плану

## Контекст и проблема

Все клиенты подключены как **самохостед iikoWeb** (`IikoWebClient`, `/resto/api/v2/`),
у которых iiko **не отдаёт `DishCostSumInt`** (себестоимость проданных блюд) без
отдельной лицензии (`iiko.py:449` `supports_cost = False`). Поэтому текущий
`/api/foodcost` (`api.py:1693`) для них честно отвечает «Себестоимость недоступна
на вашей лицензии» (`api.py:1758-1770`) и фудкост-% не показывает вообще ни у кого.

Решение: **считать себестоимость самим** из данных, которые iikoServer всё же
отдаёт — техкарты (нормы) × учётные цены ингредиентов (из остатков). Feasibility
подтверждена live-probe на сервере Saya (`saya-co.iiko.it/resto`):
- `assemblyCharts/getPrepared` → развёрнутая техкарта, `items = [{productId, amount}]` (норма).
- `reports/balance/stores` → 6587 записей `{store, product, amount, sum}` → цена = `sum/amount`.
- `documents/export/incomingInvoice` (v1) → реальные приходные цены (fallback).

## Зафиксированные продуктовые решения

- **Где:** заменяет текущий экран фудкоста (вкладка **Расходы**), период **месяц**,
  сравнение с нормой (существующая `NORM_PCT`). Облачный путь (`supports_cost=True`)
  НЕ трогаем.
- **Триггер:** **кнопка «Посчитать фудкост»**, результат **кешируется на сутки**
  (не грузим iiko при каждом открытии).
- **Показываем:** общий фудкост-% + норма/отклонение; **покрытие** (сколько %
  себестоимости реально посчитано); **топ блюд по вкладу в кост**.
- **Подпись:** «теоретический фудкост по техкартам» (не фактический по списаниям).

## Конвейер расчёта (весь на iikoServer)

```
1. OLAP продажи по блюдам за период → productId + кол-во продано + выручка блюда
2. getPrepared(productId, дата) → ингредиенты [{productId, норма}]   (кеш техкарт, TTL сутки)
3. balance/stores → { productId ингредиента : Σsum/Σamount = цена }  (1 запрос, кеш)
4. свёртка:
     себест_блюда   = Σ(норма_ингр × цена_ингр)
     себест_период  = Σ(себест_блюда × кол-во_продано)
     фудкост_%      = себест_период / выручка_период × 100
     покрытие_%     = доля себестоимости, у которой нашлась цена
```

**Матчинг блюдо→productId:** OLAP `_foodcost_month` сейчас группирует по `DishName`.
Для техкарты нужен GUID блюда. Подход: строим карту `имя→productId` из
`products/list` (probe: 1668 позиций с `id`/`name`/`type`, уже доступно), кешируем.
Если у iikoWeb OLAP есть измерение GUID блюда (`DishId`) — использовать его как
более надёжное (уточнить при реализации; матчинг по имени — рабочий fallback).

## Компоненты (файлы)

### `iiko.py` — новые методы `IikoWebClient`
- `get_assembly_prepared(product_id: str, date: str) -> List[dict]` — GET
  `/api/v2/assemblyCharts/getPrepared?key&date&productId`; возвращает
  `preparedCharts[0].items` (список `{productId, amount}`), [] если техкарты нет.
- `get_stock_prices() -> Dict[str, float]` — GET `/api/v2/reports/balance/stores`;
  агрегирует по продукту `Σsum/Σamount`, возвращает `{productId: unit_cost}`
  (пропускает продукты с `amount<=0`).
- (Опц. этап 2) `get_incoming_prices(date_from, date_to) -> Dict[str, float]` —
  парсит XML `documents/export/incomingInvoice`, последняя приходная цена по продукту.

### `api.py` — оркестратор и гейт
- `_foodcost_from_recipes(client, org_id, date_from, date_to) -> dict` — реализует
  конвейер выше; возвращает `{fact_pct, fact_sum, coverage_pct, dishes, method:"recipes"}`.
  Кеш техкарт — модульный dict `{(org,productId): (ts, items)}`, TTL 24ч.
- В `foodcost()` (`api.py:1693`): если `client.supports_cost` → текущий путь; иначе →
  `_foodcost_from_recipes`. Результат кладём в существующий кеш (`_set_cached`,
  TTL суток — уточнить/выставить 24ч для этого пути).
- Ответ (расширяем текущий resp): `norm_pct`, `fact_pct` (посчитанный, НЕ None),
  `diff_pct`, `norm_sum`, `fact_sum`, `coverage_pct` (новое), `cost_available: true`,
  `method: "recipes"`, `dishes[:20]` — топ по вкладу в себестоимость.

### `index.html` — вкладка Расходы
- Кнопка **«📊 Посчитать фудкост»** на месте плашки «недоступно».
- По нажатию: POST/GET к `/api/foodcost` (с флагом принудительного пересчёта или
  просто с кеш-логикой на бэке), спиннер, затем рендер: общий % vs норма, плашка
  покрытия («посчитано X% себестоимости»), топ блюд по косту.
- Если покрытие < 70% — плашка-предупреждение «оценка неполная: добавьте приходные
  цены / техкарты в iiko».

## Краевые случаи (честность важнее красоты)

- Ингредиент без остатка (нет в balance) → пробуем цену из наших `bot_invoices`
  (этап 2); нет и там → ингредиент не учитывается, **снижаем покрытие**.
- Блюдо без техкарты (`getPrepared` пустой) → пропуск, не ломаем расчёт.
- Выручка = 0 → фудкост не считаем, показываем «нет продаж за период».
- Все техкарты/цены пустые → возвращаем честный warning (как сейчас), не 0%.
- Единицы: норма и `sum/amount` — в базовой единице продукта, совпадают (iiko).
- Размеры блюд (`productSizeAssemblyStrategy`) — MVP берёт общую техкарту (COMMON).

## Нагрузка на iiko-сервер

- Считаем **только по проданным** блюдам за период (не по всем 624), не по всей
  номенклатуре.
- `getPrepared` — по блюду; параллелим пачками (напр. 5-8 одновременно), **кеш
  техкарт TTL 24ч** (техкарты меняются редко).
- `balance/stores` и `products/list` — по одному запросу, кеш.
- Триггер — кнопка + кеш результата на сутки: iiko не дёргается на каждом открытии.
- Сессию iikoServer закрываем/переиспользуем через существующий `_ensure_token`.

## Тестирование

Pytest в проекте нет. Проверяем:
- **verify-скрипт** на чистой функции свёртки: подаём мок техкарт (нормы),
  мок цен, мок продаж → проверяем ожидаемые `fact_sum`, `fact_pct`, `coverage_pct`
  (включая случаи: ингредиент без цены → покрытие < 100%; блюдо без техкарты →
  пропуск; выручка 0).
- Доступность API уже подтверждена live-probe (getPrepared/balance/incomingInvoice).
- Бот-эндпоинт — `py_compile` + ручная проверка на реальном сервере владельцем
  (НЕ автоматизируем live-вызовы к его проду в CI/субагентах).

## Этапы

1. **MVP:** методы клиента (getPrepared, stock_prices) + `_foodcost_from_recipes`
   (цена из остатков) + гейт в `/api/foodcost` + кнопка/рендер в Расходах +
   покрытие + топ блюд. verify-скрипт на свёртку.
2. Fallback цен из `bot_invoices` для ингредиентов с нулевым остатком.
3. (Позже) фактический фудкост через списания/остатки (± изменение запасов).

## Не входит

- Облачный путь (`supports_cost=True`) — не меняем.
- Фактический фудкост по списаниям — отдельный будущий этап.
- Разбивка по категориям блюд — YAGNI (не выбрано).
- Автоматический/фоновый расчёт — отклонён в пользу кнопки+кеш.
