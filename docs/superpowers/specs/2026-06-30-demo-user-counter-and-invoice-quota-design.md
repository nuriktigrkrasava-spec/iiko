# Дизайн: счётчик юзеров демо-бота + лимит накладных (монетизация)

**Дата:** 2026-06-30
**Ветка:** feat/demo-trial (продолжение)
**Статус:** утверждён владельцем, готов к плану реализации

## Контекст

Стек: один FastAPI-апп (`api.py`, ~5200 строк) + SQLite (`database.py`). Демо-бот и
основной бот живут на одном бэкенде, переключаются флагом `DEMO_ONLY`. Webhook
Telegram — `telegram_webhook()` (`api.py:4537`). Распознавание накладных через
Claude (Sonnet 4.6, `claude_api.py:130`). Биллинг сегодня ручной (менеджер
`@wiregroup`).

Цель — две фичи:
1. Счётчик новых юзеров демо-бота с атрибуцией источника и пушем владельцу.
2. Лимит распознавания накладных как ядро монетизации платной подписки.

Robokassa (платёжный шлюз) **в этот объём не входит** — рассмотрена, отклонена;
докупка пакетов делается вручную.

## Зафиксированные бизнес-решения

- Подписка **30 000 ₸/мес** = **200 распознанных накладных на аккаунт**.
- Сверх — единый пакет **+100 накладных за 8 000 ₸**, можно брать многократно.
- Лимит **на аккаунт** (`telegram_id`), не на клиента-сеть. 8 филиалов = 8 аккаунтов
  = 8×200 = 1600 накладных. Изоляция по филиалу сохраняется (см. текущую модель
  `restaurants.telegram_id, organization_id`).
- Счёт **по документам**: 1 накладная = 1 списание, даже если несколько фото.
- Себестоимость распознавания ~25 ₸/накладная (Sonnet 4.6: $3/1M вход, $15/1M
  выход; ~2400 вход + ~2000 выход токенов). При 200/30к маржа ~83%.
- Источник новых юзеров — Telegram deep-link `?start=<канал>` + дата/время.
- Пуш о новом юзере — владельцу на `telegram_id = 8727082281`.

## Фича 1 — Счётчик новых юзеров демо-бота + источник

### Захват источника
Telegram deep-link `t.me/<bot>?start=whatsapp` приходит в обработчик `/start`
(`api.py:4792`) как `message.text == "/start whatsapp"`. Сейчас параметр
игнорируется. Парсим токен после `/start`; если его нет — источник `direct`.
Каналы задаются раздачей разных ссылок (`whatsapp`, `instagram`, `wiregroup`, …).

### Хранение
Новая таблица `user_acquisition` (в `init_db()`, идиома `CREATE TABLE IF NOT
EXISTS` + `ALTER ... ADD COLUMN` в try/except, как остальные):

| Колонка | Тип | Назначение |
|---|---|---|
| `telegram_id` | INTEGER PK | юзер |
| `username` | TEXT | @username на момент входа |
| `source` | TEXT | значение start-параметра или `direct` |
| `first_seen_ts` | INTEGER | unix-время первого `/start` |

Запись `INSERT OR IGNORE` при **первом** `/start` — юзер фиксируется сразу, до
подключения iiko (сегодня он попадает в `users` поздно — `api.py:861/871/892/901/4508`).
Хелперы в `database.py`: `record_acquisition(telegram_id, username, source) -> bool`
(возвращает True, если строка создана) и геттеры для статистики.

### Пуш владельцу
Когда `record_acquisition` создал новую строку (first-touch), демо-бот шлёт на
`OWNER_CHAT_ID = 8727082281`:
```
🆕 Новый юзер @username
Источник: whatsapp
30.06.2026 14:32
```
Повторный `/start` того же юзера владельца не дёргает. `OWNER_CHAT_ID` — новая
константа/`.env`-переменная.

### Команда /stats
Админ-команда в webhook (ответ только если `chat_id == OWNER_CHAT_ID`): всего
юзеров, за сегодня, за неделю, разбивка по источникам.
```
👥 Всего: 137
За сегодня: 6 · за неделю: 41
По источникам: whatsapp 88 · instagram 32 · direct 17
```

## Фича 2 — Лимит распознавания накладных (основной бот)

### Хранение
Новая таблица `invoice_quota` (обобщает текущую `demo_invoice_usage`,
`database.py:128`):

| Колонка | Тип | Назначение |
|---|---|---|
| `telegram_id` | INTEGER PK | аккаунт |
| `period_start_ts` | INTEGER | начало текущего расчётного месяца |
| `used` | INTEGER | распознано в этом периоде |
| `base_limit` | INTEGER, default 200 | базовый лимит подписки |
| `extra` | INTEGER, default 0 | докупленные пакеты |
| `plan_active` | INTEGER, default 0 | активна ли платная подписка |

Хелперы в `database.py` по образцу `inc_demo_invoice_count` (`database.py:213`):
`get_quota(telegram_id)`, `inc_quota_used(telegram_id)`, `add_quota_extra(telegram_id, n)`,
`reset_quota_if_due(telegram_id)`.

### Логика гейта
Перед распознаванием — в `_recognize_invoice_and_create_pending()` (`api.py:4395`)
и текстовом пути (`api.py:4811`):
1. `reset_quota_if_due` — если `now > period_start + 30*86400`, обнулить `used` и
   `extra`, `period_start = now`.
2. Если `used >= base_limit + extra` → распознавание **не** запускается; бот шлёт:
   ```
   📦 Лимит 200 накладных в этом месяце исчерпан.
   Докупить +100 за 8 000 ₸ — напишите менеджеру.
   (пакет действует до конца месяца)
   ```
   + inline-кнопка на `https://t.me/wiregroup`.
3. Иначе распознаём и в конце (`api.py:4446`) `inc_quota_used` (один раз на
   документ).

Это заменяет хардкод `_demo_block_if_used` (`api.py:4377`, «≥1»). Демо-режим
(`DEMO_ONLY`) сохраняет свой бесплатный лимит как отдельную ветку; платный лимит
200 применяется к аккаунтам с `plan_active`.

### Активация подписки (plan_active)
Платёжного шлюза нет, поэтому подписка активируется вручную владельцем после
оплаты (Kaspi/счёт): админ-команда `/activate <telegram_id>` → `plan_active = 1`,
`period_start_ts = now`, `used = 0`. Альтернатива на обсуждение: считать любой
аккаунт основного бота с подключённым iiko платным по умолчанию (тогда
`plan_active` не нужен, гейт смотрит только на `used` vs `base_limit + extra`).
Решение зафиксировать на этапе плана реализации.

### Докупка без платёжки
Платёжный шлюз не подключаем. Клиент пишет менеджеру и платит вручную
(Kaspi/счёт). Владелец начисляет пакет админ-командой `/addquota <telegram_id>
<кол-во>` → `add_quota_extra(telegram_id, n)`. Доступна только с `OWNER_CHAT_ID`.

### Константа
`DEMO_PLAN_INVOICES = 300` (`api.py:500`, сейчас только в тексте оффера, нигде не
enforced) → `200`; используется как `base_limit`.

## Что НЕ входит в объём

- **Robokassa / любой платёжный шлюз.** Нет `.env`-кредов, таблицы `payments`,
  Result/Success/Fail URL. Докупка — ручная через менеджера + `/addquota`.
- **Подписка через эквайринг.** 30к остаётся ручным выставлением (Kaspi/счёт) —
  гнать B2B-суммы через 3%-эквайринг расточительно.
- Группировка аккаунтов в «клиента-сеть» (`org_group`) — не нужна, лимит на аккаунт.

## Персистентность / миграции

SQLite, без ORM. Новые таблицы и колонки — в `init_db()` (`database.py:47`):
`CREATE TABLE IF NOT EXISTS` + идемпотентные `ALTER TABLE ... ADD COLUMN` в
try/except. Фреймворка миграций нет — следуем текущей идиоме.

## Краевые случаи

- Юзер, у которого уже есть строка в `user_acquisition`, повторным `/start` не
  создаёт дубль и не шлёт пуш (`INSERT OR IGNORE` + проверка факта вставки).
- `/start` без параметра → `source = direct`.
- Распознавание упало с ошибкой → `used` не инкрементим (инкремент только при
  успешном создании pending-накладной).
- Сброс периода ленивый (при следующем обращении аккаунта), отдельный планировщик
  не нужен.
- `/addquota` с несуществующим `telegram_id` → создаём строку квоты с `extra = n`
  (на случай предоплаты до первого распознавания).
